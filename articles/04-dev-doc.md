# 开发文档：一片 3D 森林的 AI 协作实录

这份文档记录《晨光森林 · 蚂蚁运粮》从一句话需求到上线作品的完整过程——用了什么模型、什么 Agent 工具、提示词是怎么写的，以及哪几轮是 AI 自己发现问题、自己改掉的。

写它是因为"AI 做了个 3D 场景"这句话没有信息量。真正有信息量的是：**提示词怎么写才不返工**，以及 **Agent 的工作闭环长什么样**。

---

## 一、技术栈与角色分工

| 角色 | 承担 |
|---|---|
| **人类** | 提出目标、看效果、给判断、定边界 |
| **模型** | DeepSeek（对话推理 + 代码生成） |
| **Agent 工具** | WorkBuddy —— 文件读写、命令执行、浏览器自动化（Chrome DevTools MCP）、页面截图回读 |

关键不在模型大小，在**Agent 有没有眼睛和手**。

这一轮里真正起决定作用的不是"模型能不能写 Three.js"，而是它能：

1. 把 HTML 写到磁盘
2. 起一个本地 HTTP 服务
3. 用无头浏览器打开、截图
4. **把截图读回自己的上下文**
5. 看见「雾太浓了」「土丘是黑的」，然后改代码
6. 再截一次，对比

没有这个闭环，模型只能盲写代码，交付物是一份"看起来对"但没人验证过的文件。

## 二、第一轮提示词：把需求写成可验收的样子

原始输入（一字未改）：

> 用threejs最新的版本，做一个3D场景的动画显示，在森林的地面，有一群蚂蚁排成长长的队列，不停的在传递食物块，从场景的一边传递到场景内的一个蚂蚁洞内。场景能旋转和缩放查看。场景的内容要丰富，有大树，有蘑菇，有树叶，有露水，所有地面的树枝和青苔等应该有的内容。有好的光照，是清晨的阳光。

这条提示词有三个值得学的地方：

**① 指定版本** —— "最新的版本"。模型于是去查 npm registry，确认当时是 r186.1，而不是凭记忆写 r150 的 API。后来的所有兼容性判断（`Clock` 废弃、`PCFSoftShadowMap` 移除）都是基于这个查询结果。

**② 用名词枚举内容** —— 大树 / 蘑菇 / 树叶 / 露水 / 树枝 / 青苔。这是"清单式验收"：交付时逐项对，缺一个就是没做完。

**③ 给了氛围词** —— "清晨的阳光"。这不是装饰，它决定了光照角度、色温、雾的颜色一整套参数。

**缺的是什么？** 没有验收阈值。所以第一版回归时，人类只能靠"看"来判断。

## 三、Agent 的自我迭代：15 次截图

第一版到能交付，中间隔了约 15 轮「截图 → 读图 → 改代码」。举三个真实例子。

### 例 1：雾色和地平线不匹配

第一版画面偏灰，远处天和地之间有一条硬边。

诊断：雾色 `0xb8c8c9` 与天空纹理底部颜色不一致。

改法：

```js
// 改前
scene.fog = new THREE.Fog(0xb8c8c9, 24, 62);

// 改后：雾色从天空纹理地平线附近取样
scene.fog = new THREE.Fog(0xe3cfa4, 22, 66);
```

一条颜色对齐，画面从"一个方形地板"变成"一片林子"。

### 例 2：苔藓像浮萍

第一版的苔藓是独立随机小球，近看是一片片绿色圆盘浮在土上。

改法是把分布从「随机撒点」换成「成簇生长」：先生成 46 个斑块中心，实例围绕中心做高斯偏移，尺寸随距中心的距离衰减。

```js
const rad = Math.pow(rnd(), 0.5) * c.r;
const s = rr(0.13, 0.40) * (1 - Math.pow(rad / c.r, 2) * 0.5);  // 边缘更小
```

同时把每个苔藓丘的高度压到宽度的 10%–26%，让它贴合地面而不是立着。

### 例 3：LatheGeometry 的法线陷阱

蚁穴土丘原本是纯黑的。用脚本把顶点法线打出来：

```json
{"r": 1.05, "y": 1.05, "ny": -0.95}
```

`ny = -0.95`，法线朝下。原因不是 `computeVertexNormals()` 用错了，而是**剖面点的顺序**——从内向外给点时，旋转体的绕序让法线朝内。

修法只有一行：把剖面数组倒过来，从外向内。

```js
const prof = [
  new THREE.Vector2(3.05, -0.05),   // 外
  // …
  new THREE.Vector2(0.60, 0.66)     // 内
];
```

这类问题**靠读代码是发现不了的**。必须看见那块黑色，才会去查法线。

## 四、第二轮提示词：用户反馈的写法

第一次交付后，人类给了四条反馈（原文）：

> **树太矮，太小，不像森林**
> **蚂蚁每个都带一个食物，但不互相扔**
> **蚂蚁窝洞口有高度，不应该透明，蚂蚁应该爬上去才下去，要有物理逻辑，不能穿过去**
> **蚂蚁有体积，不能重叠，所以东西都有体积。**

这四条写了两种东西：**现象** 和 **期望状态**。

- "树太矮，太小" → 现象（可量化：13.5 米 → 25 米）
- "不像森林" → 期望（抽象，但结合现象就能推出方向：要柱廊感、要仰视）
- "蚂蚁应该爬上去才下去" → 期望（明确了因果：必须先到达高处）
- "不能重叠，所以东西都有体积" → **判据**（这句话把模糊的"自然一点"变成了可检查的规则）

**最有效的一条是最后一条。** 因为它给了判定标准：两者中心距 > 两者半径和，否则不合法。模型可以据此反推——间距要大于体长，速度必须一致，否则队形会漂移。

### 这四条对应的改动

| 反馈 | 根因 | 修法 |
|---|---|---|
| 树太矮 | H = 13.5，树干直径 2.5 米 | H → 25，底部直径 6 米，主树 3→6 棵，远景 26→46 棵 |
| 食物互扔 | 有 carry/toss 状态机 | 删掉整套状态机，食物改挂为蚂蚁子节点 |
| 蚁穴穿模 | 蚂蚁 y 恒等于地面高度 | 引入高度场 `surfaceHeight()` |
| 蚂蚁重叠 | 每只速度随机 ±6% | 全体同速，间距 0.95 m > 体长 0.55 m |

### 蚁穴那一条展开讲

"要有物理逻辑，不能穿过去"这句话，逼出了一个设计决策：**不接物理引擎**。

需要的不是刚体动力学，是一个确定性的高度查询：

```js
function surfaceHeight(x, z) {
  return terrainHeight(x, z) + moundHeight(holeDist(x, z));
}
```

`moundHeight(r)` 用两段剖面线性插值——土丘外表面和洞内漏斗。因为剖面点是线性连接的，插值和几何完全贴合。

实测轨迹（这也是验收证据）：

| 到洞口距离 | 高度 | 状态 |
|---|---|---|
| 4.64 m | 0.26 m | 平地 |
| 2.65 m | 0.42 m | 踏上外坡 |
| 1.66 m | 0.94 m | 翻过唇边 |
| 0.03 m | -0.84 m | 入洞，缩放 0.13 |

**如果提示词只说"蚂蚁要进洞"，AI 大概率会做成"走到洞口缩小消失"——那正是第一版的问题。** 说清"爬上去才下去"，才得到高度场方案。

## 五、第三轮提示词：四个字的反馈

> **阳光穿过树干了，不对**

这是最短的一次反馈，也是最精准的一次。

现象描述只用了八个字，但足以定位问题：丁达尔光柱横跨场景，压在树干上。

诊断过程：光柱长 16–22 米，斜射时水平跨度约 14 米，必然与树干相交。`depthTest` 只能挡住"树干后面"的部分，"树干前面"那段仍然叠在树干上。

修法三步（详见技术文章）：

```js
// ① 每棵树登记水平碰撞体
TREE_COLLIDERS.push({ x: baseX, z: baseZ, r: 2.4 * scale });

// ② 沿光柱轴线采样检测，撞树就重试
function beamHitsTree(cx, cy, cz, h) {
  for (let s = -0.5; s <= 0.5001; s += 0.07) {
    const px = cx + lightDir.x * h * s;
    const pz = cz + lightDir.z * h * s;
    for (const t of TREE_COLLIDERS) {
      if (Math.hypot(px - t.x, pz - t.z) < t.r + 0.35) return true;
    }
  }
  return false;
}

// ③ 缩短减淡：16–22 → 6–10.5 米，透明度 0.032 → 0.014–0.028
```

值得注意的是：**这个问题在第一轮内部迭代时出现过一次，我当时只是把光柱调淡了，没根治**。人类一句话点出来，才去做了碰撞避让。

这说明 Agent 的自检有盲区——它会优先解决"看起来最丑的"，而不是"逻辑最错的"。

## 六、Agent 工作流的实际形态

```
人类一句话需求
   ↓
模型读需求 → 查版本（npm registry / CDN 探活）
   ↓
写 index.html（单文件，零外部资源）
   ↓
起本地服务 → 无头浏览器打开 → 截图
   ↓
【关键】截图回读进上下文
   ↓
读图诊断 → 改代码 → 再截图
   ↓  （循环 ~15 次）
人类查看 → 给反馈
   ↓
再循环（3 轮）
   ↓
发布：GitHub 仓库 + Pages + 平台作品 + 社区文章
```

几个实现细节：

**截图怎么落盘**：Chrome DevTools MCP 的 `take_screenshot` 在这个环境里存不进指定目录，于是改成页面内导出——`renderer.domElement.toDataURL()` 拿到 base64，`fetch` POST 到一个本地 Python 服务器落盘。注意 WebGL 的 canvas 必须在**同一帧内**取图，否则缓冲区已被清空。

**模型看到的图**：截图回读后，模型能直接看出"蘑菇是塑料感""雾太白""土丘是黑的"。这类判断不需要人，但需要**图**。

**GitHub 推送失败**：这个网络环境里 `github.com:443` 被阻断，`git push` 全部超时，但 `api.github.com` 正常。于是所有提交改走 REST API：

```python
PUT /repos/{owner}/{repo}/contents/{path}
{ "message": "...", "content": "<base64>", "sha": "<已有文件的 sha>" }
```

Pages 也用 API 启用：`POST /repos/{owner}/{repo}/pages` + `source[branch]=main`。

## 七、哪些活是模型干不了的

诚实记录三个 Agent 失效的场景：

**① 视觉审美的最终判断。** 模型能判断"这里太黑了"，但判断不了"这个构图好不好"。第一版相机位置调整了四次，都是靠人眼睛拍板。

**② 越界自检。** 光柱穿树的问题模型自己发现过一次，但选择了"调淡"而不是"根治"。它倾向于用最小改动消除视觉不适，而不是修复逻辑错误。

**③ 平台规则的理解。** AIGPart 的"作品审核通过后才创建论坛版面"这条，是从 `POST /api/forum/threads` 返回的 400 和 boards 列表的差异里反推出来的，不是文档里写的。

## 八、可复用的提示词模板

从这次协作里提炼出来的写法：

```
【目标】一句话说清最终形态
【清单】把要有的东西按名词列出来，逐项可验收
【判据】给可量化的约束（尺寸、间距、比例、不能出现什么）
【氛围】用形容词定调，它会决定一整套参数
【参考】如果有，给一个已知的好例子
```

反例（这次没出现，但常见）：

- ❌ "做得好看一点" —— 无判据
- ❌ "用最佳实践" —— 无边界
- ❌ "参考一下 xxx" 但不说参考什么 —— 模型会猜
